## 0. 结论先行（TL;DR）

1. **核心不是"让模型读剧本"，而是"把剧本变成状态机，让模型只负责把状态翻译成人话"。**
   模型管叙事，程序管事实。所有血量、理智、线索、场景、回合都必须落在结构化数据里，模型每回合只拿到"这一回合该知道的那一小块"。
2. **六项诉求 = 五个能力域 + 一条主线**：角色卡域、规则引擎域、剧本运行时域、回合调度域、复盘域；主线是**事件日志（event sourcing）**——它同时是存档、回放、审计和 debug 的唯一事实源。
3. **剧本和规则不能让 LLM 临场读**。剧本要离线"导入 → 结构化 → 人工校对"；规则要写成代码/表。把长 PDF 塞进上下文跑长团，必然幻觉、漏线索、剧透。
4. **与 suggarchat 的分工建议"混合模式"**：`coc_keeper` 插件管状态机 / 规则 / 回合调度；sugarchat 当**叙事渲染器与 NPC 台词引擎**，通过 `on_before_chat` 注入"本回合事实包"、`on_chat` 做输出后处理。**不能让 suggarchat 的聊天记忆当游戏状态**。
5. **最小可玩闭环（P1）比"大而全"重要**：一个手写的小模组（3 场景 / 5 线索 / 2 NPC）+ 行动协议 + 检定 + 叙事，能在群里跑 20 分钟，就已经证明架构成立。之后再加剧本导入和复盘。
6. **复盘的唯一正解是事件溯源**：每个动作、每次骰点、每次状态变更都 append 到事件表，replay 只是"重放 + 渲染"，不依赖模型回忆。
7. **别把"改状态"的权力交给模型**：agent / 工具调用只给**只读查询**；HP、SAN、线索、场景推进必须由程序执行（详见 7.6）。让模型"查"可以，让它"改"不行。
8. **KP 的调控要"可查"，不要"暗改"**：放水只改后果与信息、绝不改骰点；惩罚只针对 OOC 破坏行为，社交处罚交给人（详见 6.8、6.9）。

## 1. 需求拆解

### 1.1 原始诉求逐条拆解

| #   | 你的原话                     | 本质是什么                     | 真正的难点                                  | 归属模块           |
| --- | ------------------------ | ------------------------- | -------------------------------------- | -------------- |
| 1   | 创建、管理角色卡（玩家 PC + 剧本 NPC） | 结构化数据 + 编辑界面 + 规则校验       | 车卡体验（群聊里逐条问答很痛苦）、字段与规则绑定、NPC 的"秘密信息"隔离 | 角色卡域           |
| 2   | 读懂跑团剧本和跑团规则              | 非结构化文本 → 可执行结构            | 剧本是 PDF/Word，含表格与剧透；规则是自然语言，模型记不牢也不算得准 | 剧本运行时域 + 规则引擎域 |
| 3   | 调度和管理整个剧本                | 场景图 + 线索可见性 + 触发条件 + 结局判定 | 状态一致（谁在哪、知道什么）、防剧透、分支收敛                | 剧本运行时域         |
| 4   | 控制每个回合玩家的行动              | 行动协议 + 排序 + 合法性校验 + 检定    | 多人抢话、自然语言 → 结构化动作、超时与挂机                | 回合调度域          |
| 5   | 产出复盘 replay              | 事件溯源 + 渲染                 | 事实完整性（模型不可靠）、可读性、指标                    | 复盘域            |
| 6   | suggarchat 担任剧本演出和对话控制   | LLM 接入层与钩子                | 记忆污染、人格串味、输出长度/格式、双回复                  | 接入层            |

### 1.2 三条贯穿全局的原则

**原则一：状态与叙事分离。**

```
玩家说："我想翻一下那本日记。"
        ↓
[程序] 意图解析 → 动作 {type: investigate, target: 日记, scene: 书房}
[程序] 合法性校验 → 日记在本场景且未被翻过
[程序] 规则判定 → 侦查 检定（是否需要、难度、奖励骰）
[程序] 掷骰 → d100=37 ≤ 65 成功
[程序] 状态变更 → clue:日记-缺失页 discovered_by=P1；写入事件表
[程序] 事实包 → {动作、检定结果、新线索的"玩家可见描述"、NPC 反应提示}
        ↓
[模型] 只做一件事：把事实包写成 2-4 句有氛围的中文
```

模型永远不决定"有没有线索"，只决定"怎么说"。

**原则二：玩家可见 / KP 不可见的硬隔离。**
每个线索、NPC、场景都存两份描述：`player_text`（可进模型提示词）与 `keeper_text`（只进规则判定，不进叙事提示词）。**剧透是这类系统最容易翻车的地方**，必须在数据层切开，而不是靠提示词"请不要剧透"。

**原则三：一切可重放。**
掷骰记录原始点数与目标值（而不是只记"成功"），状态变更记录 before/after。这样 replay、争议仲裁、bug 复现都有据可查。

## 2. 整体架构

### 2.1 分层

```
QQ 群 / 私聊
   │  OneBot V11（NapCat）
   ▼
NoneBot2 ──► coc_keeper 插件（本设计的主体）
   │            ├─ 命令层：/coc 系列（开局、行动、状态、结束）
   │            ├─ 回合调度器：收集声明 → 排序 → 逐个结算
   │            ├─ 规则引擎：d100 检定 / 对抗 / 伤害 / SAN
   │            ├─ 剧本运行时：场景图 + 线索 + 触发器 + 结局
   │            ├─ 角色卡服务：PC/NPC 读写 + 校验
   │            ├─ 叙事适配器：拼"事实包"→ 调 suggarchat/LLM → 后处理
   │            └─ 复盘器：事件表 → 战报
   │
   ├─► SQLite（独立库 data/coc_keeper/coc.sqlite3，不复用 suggarchat 记忆库）
   │
   └─► suggarchat（叙事渲染 / NPC 台词）
          ▲ on_before_chat 注入事实包
          ▼ on_chat 后处理（截断、分条、去格式）

浏览器 ──► /ai-config/ 配置台新增「跑团」页（角色卡 / 模组 / 会话监控）
```

### 2.2 一次行动的时序（含模型调用边界）

```
1. 玩家在群里发言（或私聊 KP）
2. 调度器判断：当前是否等这个玩家？该场景是否允许自由行动？
3. 意图解析（规则优先 + 模型兜底）：得到结构化动作
4. 动作合法性校验（场景、目标、资源、状态）
5. 规则判定：要不要检定？难度？奖励/惩罚骰？
6. 掷骰（服务端 secrets）→ 结论 + 是否孤注一掷/幸运调整
7. 状态变更（HP/SAN/线索/NPC 态度/场景进度）+ 写事件
8. 拼事实包 → 调模型（≤ 预算）→ 拿到叙事
9. 输出：群消息（叙事 + 状态条）+ 必要时私聊秘密信息
10. 推进回合：是否触发场景切换 / 结局
```

**第 3 步是唯一需要模型参与的"理解"环节**，且必须可降级：解析不出来就问一句"你是想 A 还是 B？"，绝不猜。

### 2.3 与 suggarchat 的三种集成方案

| 方案                | 做法                                                                       | 优点                        | 缺点                             | 结论       |
| ----------------- | ------------------------------------------------------------------------ | ------------------------- | ------------------------------ | -------- |
| A. 全交给 suggarchat | 写两段没人维护得动的提示词，让模型自己记状态                                                   | 几乎不写代码                    | 状态不可靠、必崩；长团必失忆；剧透无法控           | ❌ 不可行    |
| B. 纯自建            | coc_keeper 自己调 DeepSeek，完全绕开 suggarchat                                  | 完全可控，格式/长度/温度都能调          | 失去 suggarchat 的人设、记忆摘要、限流、失败重试 | 可行但重复造轮子 |
| C. 混合（推荐）         | coc_keeper 管状态/规则/回合；sugarchat 只当"笔"：`on_before_chat` 注入事实包，`on_chat` 收尾 | 状态可控 + 复用现成的 LLM 通道/重试/限流 | 需要钩子纪律（见 7 章）                  | ✅ 推荐     |

混合模式下要额外做三件事（否则会打架）：

1. **跑团群关闭 suggarchat 的聊天记忆**（`group_config` 或独立开关），避免上一局的闲聊记忆污染本局叙事；
2. **只让 KP 的叙事请求进入模型**：其余群消息不触发 suggarchat 自动回复（否则一次行动会收到两条回复）；
3. **输出后处理**：截断到 2-4 句、去掉"作为 KP 我认为…"这类元叙述、必要时按 `。` 分条发送。

## 3. 领域模型

### 3.1 角色卡（COC 7e）

**PC（玩家角色）**：调查员。字段与规则强相关，必须校验。

| 字段组 | 内容                                                                       |
| --- | ------------------------------------------------------------------------ |
| 身份  | 姓名、玩家 QQ、职业、年龄、性别、居住地                                                    |
| 属性  | STR / CON / SIZ / DEX / APP / INT / POW / EDU（3-18 或 ×5 后的百分比）、LUK 3d6×5 |
| 派生  | HP = (CON+SIZ)/10 向下取整、MP = POW/5、SAN = POW、MOV、DB（伤害加值）、体格              |
| 技能  | `{技能名: 值}`，含职业/兴趣分配；默认值表（如侦查 25、聆听 20、图书馆 20、闪避 = DEX/2）                 |
| 状态  | 当前 HP、当前 SAN、当前 MP、当前 LUK、重伤/濒死/临时疯狂/不定性疯狂、负伤标记                          |
| 物品  | 随身物品、武器（伤害/射程/次数）、法术（若有）                                                 |
| 叙事  | 背景、动机、外貌、关键时刻（供模型拿捏语气）                                                   |
| 元数据 | 创建时间、最后更新、所属团、是否已死亡/退役                                                   |

**NPC（剧本角色）**：除了属性，还有两类关键信息。

| 字段组     | 内容                                               |
| ------- | ------------------------------------------------ |
| 公开面     | 名字、身份、外貌、对玩家的初始态度、说话风格（给模型定调）                    |
| **秘密面** | 真实身份、知道的情报、目标、恐惧、会在什么条件下翻脸 → **只进规则判定，绝不进叙事提示词** |
| 数值      | 属性/技能（简化到"关键技能 + 战斗数值"即可）                        |
| 出场条件    | 属于哪个场景、触发条件、是否可被杀/可被救                            |

> 设计取舍：**NPC 不需要完整车卡**。跑团里 90% 的 NPC 只需要 3-5 个数值 + 一段秘密 + 一句语气说明。完整车卡留给"重要反派"。

### 3.2 模组（剧本）结构

采用**场景图（scene graph）+ 线索 + 触发器**，而不是"一章一章的散文"：

```
module
├─ meta：标题、时代、地点、人数、预计时长、难度、内容警告
├─ background：KP 用背景真相（永不进玩家提示词）
├─ scenes[]
│   ├─ id / title / summary
│   ├─ player_text     # 玩家进入场景时看到的描写（可进提示词）
│   ├─ keeper_text     # 场景真相、隐藏要素（不进提示词）
│   ├─ npcs[]          # 出场 NPC
│   ├─ clues[]         # 可发现线索（带发现条件）
│   ├─ exits[]         # 通往哪些场景 + 条件
│   └─ triggers[]      # 进入/停留/离开时触发的效果
├─ timeline[]：外部的"世界时钟"事件（第 3 天仪式开始…）
├─ endings[]：结局条件 + 结局文本
└─ handouts[]：手图、信件、报纸剪报（图片/文本）
```

**线索（clue）**是这里最关键的实体：

| 字段                   | 说明                           |
| -------------------- | ---------------------------- |
| `discover_condition` | 什么动作能发现（技能阈值、特定物品、特定 NPC 对话） |
| `player_text`        | 发现后给玩家看的内容（可进模型提示词）          |
| `keeper_text`        | 这条线索的真正含义（不进提示词）             |
| `importance`         | 主线 / 支线 / 干扰项                |
| `leads_to`           | 指向哪些场景/线索（用于"卡关检测"）          |

有了 `leads_to` + `importance`，运行时才能做**卡关提示**：玩家转了两圈没找到主线线索时，KP 可以用"灵感/幸运"或 NPC 提示推一把，而不是把玩家晾死。

### 3.3 会话与回合

```
session（一局）
 ├─ campaign_id, status(running/paused/ended), current_scene_id
 ├─ turn_no
 ├─ party[]：本局参与的 PC
 └─ clock[]：世界时间线指针

turn（一个回合）
 ├─ no, declared_actions[]（谁声明了什么）
 ├─ resolution[]（逐条结算：动作 → 检定 → 结果）
 └─ narrative（本回合产出的文本）
```

**回合的粒度建议按"场景内的一个行动轮"来切**，而不是每条消息一回合：

- 场景切换 = 大回合结束；
- 一个行动轮 = 所有在场玩家各做一件事（或明确"我不动"）。

### 3.4 事件日志（复盘的唯一事实源）

```
event(id, session_id, seq, type, actor, payload_json, created_at)
```

`type` 取值示例：`session_start` / `scene_enter` / `action_declared` / `roll` / `state_change` /
`clue_found` / `npc_talk` / `san_check` / `combat_round` / `scene_exit` / `ending` / `session_end` /
`ooc` / `tension_change` / `keeper_mercy` / `disrupt`。

**为什么必须单独存事件，而不是只存"当前状态"**：

- 复盘要按时间顺序还原（只存状态就还原不出来）；
- 玩家争议时能查"当时骰了多少"；
- 出 bug 能重放；
- 可以让复盘器独立演进出多种战报样式，不动主流程。

### 3.5 表结构草案

```sql
-- 团（一次长战役；一个群可以先后开多个团）
CREATE TABLE campaign(
  id INTEGER PRIMARY KEY, group_id INTEGER NOT NULL, module_id INTEGER,
  title TEXT, status TEXT DEFAULT 'idle', keeper_style TEXT,
  created_at TEXT, updated_at TEXT);

-- 模组（结构化后的剧本）
CREATE TABLE module(
  id INTEGER PRIMARY KEY, title TEXT, version TEXT, author TEXT,
  meta_json TEXT, background TEXT, source_path TEXT,
  scenes_json TEXT, npcs_json TEXT, clues_json TEXT,
  timeline_json TEXT, endings_json TEXT, handouts_json TEXT,
  validated INTEGER DEFAULT 0, created_at TEXT);

-- 角色卡（PC 与 NPC 共用一张表，type 区分）
CREATE TABLE character(
  id INTEGER PRIMARY KEY, campaign_id INTEGER, module_id INTEGER,
  type TEXT CHECK(type IN ('pc','npc')),
  name TEXT, owner_qq INTEGER, occupation TEXT,
  attrs_json TEXT, skills_json TEXT, derived_json TEXT, condition_json TEXT,
  items_json TEXT, public_json TEXT, secret_json TEXT,
  created_at TEXT, updated_at TEXT);

-- 会话 / 回合 / 骰点 / 事件
CREATE TABLE session(
  id INTEGER PRIMARY KEY, campaign_id INTEGER, status TEXT,
  current_scene TEXT, turn_no INTEGER DEFAULT 0,
  house_rules_snapshot TEXT,      -- 开局时的村规快照（Q1：改村规不影响进行中的局）
  started_at TEXT, ended_at TEXT);

CREATE TABLE turn(
  id INTEGER PRIMARY KEY, session_id INTEGER, no INTEGER,
  scene_id TEXT, declared_json TEXT, resolution_json TEXT,
  narrative TEXT, created_at TEXT);

CREATE TABLE roll(
  id INTEGER PRIMARY KEY, session_id INTEGER, turn_id INTEGER,
  actor TEXT, kind TEXT,            -- skill / san / damage / luck / opposed
  skill TEXT, target INTEGER, difficulty TEXT,
  bonus_penalty INTEGER, d100 INTEGER, outcome TEXT,
  visibility TEXT DEFAULT 'public',   -- public / private / kp_only（Q5）
  detail_json TEXT, created_at TEXT);

-- 村规（Q1：结构化持久化；开局快照进 session，保证复盘一致）
CREATE TABLE house_rules(
  id INTEGER PRIMARY KEY, campaign_id INTEGER,
  key TEXT NOT NULL, value_json TEXT NOT NULL,
  scope TEXT DEFAULT 'campaign',       -- campaign / scene
  version INTEGER DEFAULT 1, updated_at TEXT,
  UNIQUE(campaign_id, key, scope));

CREATE TABLE event(
  id INTEGER PRIMARY KEY, session_id INTEGER, seq INTEGER,
  type TEXT, actor TEXT, payload_json TEXT, created_at TEXT);

CREATE TABLE clue_state(
  session_id INTEGER, clue_id TEXT, discovered_by TEXT,
  discovered_at TEXT, scene_id TEXT,
  PRIMARY KEY(session_id, clue_id));
```

> 落点：**独立 SQLite 文件**（`data/coc_keeper/coc.sqlite3`），不塞进 suggarchat 的 ORM 库——
> 避免动它的迁移、避免它的记忆被我们的大表拖慢、也方便单独备份/导出战报。

## 4. 规则引擎（COC 7e 子集）

原则：**规则写死在代码里，模型不参与计算**。引擎对外只暴露 `check(actor, skill, difficulty, modifiers) -> Result`。

### 4.1 检定

| 项      | 规则                                   |
| ------ | ------------------------------------ |
| 基础     | d100 ≤ 技能值 = 成功                      |
| 难度     | 常规 = 技能值；困难 = 技能值/2；极难 = 技能值/5（向下取整） |
| 大成功    | 01（或 ≤ 技能值/5 的约定房规，需在配置里选）           |
| 大失败    | 技能 < 50 时 96-100；技能 ≥ 50 时 100       |
| 奖励/惩罚骰 | 额外十位骰，取更小（奖励）/更大（惩罚）；可叠加多颗           |
| 孤注一掷   | 失败后可重试一次，需描述额外努力；再失败 → KP 给出更严重后果    |
| 幸运消费   | 每点幸运换 1 点骰点修正；消耗后记录，幕间不回满            |

### 4.2 对抗与被动的边界

- 对抗检定：双方各掷，比较成功等级（极难 > 困难 > 常规 > 失败），同级比技能值高者。
- 需要"被动值"的地方（如聆听对抗潜行）直接用技能值当 DC，不要每次双向掷骰——群聊里一轮掷两次代价太高（延迟 + token）。

### 4.3 战斗（简化版）

| 环节   | 规则                                  |
| ---- | ----------------------------------- |
| 先攻   | 每轮按 DEX 降序；同值按声明顺序                  |
| 近战   | 格斗检定 → 对手可闪避或反击（二选一，每轮 1 次）         |
| 射击   | 射击检定，按射程/连发调整；目标可闪避（若可见）            |
| 伤害   | 武器伤害 + DB；记录每轮累计                    |
| 重伤   | 单次伤害 ≥ 当前 HP 的 1/2 → 重伤（CON 检定避免昏迷） |
| 濒死   | HP ≤ 0 → 濒死，每轮 CON 检定，直到稳定或死亡       |
| 简化取舍 | **不做**完整的部位/护甲耐久/载具规则；群聊跑团撑不住那种粒度   |

### 4.4 SAN 与疯狂

| 项     | 规则                                                    |
| ----- | ----------------------------------------------------- |
| 理智检定  | d100 ≤ 当前 SAN；失败按模组给的点数损失（如 1/1d6）                    |
| 大失败   | 损失取最大值                                                |
| 临时性疯狂 | 单次损失 ≥ 5 → INT 检定：成功则"意识到自己疯了"（触发疯狂表现），失败则"压抑"（KP 记录） |
| 不定性疯狂 | 累计损失 ≥ 初始 SAN 的 1/5 → 不定性疯狂（长期症状表）                    |
| 疯狂发作  | 由 KP 抽症状（表驱动），持续若干轮；**症状表现可以交给模型演，但"抽到哪个症状"必须程序定**    |

### 4.5 成长（幕间）

技能用过 → 打勾；幕间做成长检定（d100 > 技能值 则 +1d10）。P1 可以先只记录"用过哪些技能"，成长结算放到幕间工具里。

### 4.6 明确不做的部分（第一版）

- 法术大全 / 神话法术的完整实现（先支持模组用到的 3-5 个）；
- 载具、追逐（chase）规则的完整版；
- 房规（除非你在配置里显式打开）；
- 自动战斗数值平衡（KP 只按剧本给数值，不做动态难度）。

### 4.7 骰子与可复算

- 随机源：`secrets.randbelow(100)+1`；**记录原始点数**，不必记录种子；
- 每次掷骰写 `roll` 表，战报里原样呈现（`d100=37/65 成功`）；
- 明骰/暗骰：`roll.visibility`（`public` / `kp_only`），暗骰只在 KP 私聊或战报 KP 版里出现。

## 5. 剧本的"读懂"与运行时

### 5.1 为什么不能让模型直接读完整模组

| 问题     | 说明                                            |
| ------ | --------------------------------------------- |
| 上下文装不下 | 一个 CoC 模组 3-10 万字，模型上下文 64k-128k token，长团必然截断 |
| 幻觉     | 模型会"编"出不存在的房间、把 NPC 名字记混、提前泄露真相               |
| 无状态    | 它不知道"玩家已经知道哪些线索"，无法维持一致性                      |
| 成本     | 每回合重读全文，token 成本爆炸（见 7.5 预算）                  |
| 剧透     | 真相与玩家可见信息混在一个上下文里，模型容易说漏                      |

### 5.2 导入流水线（离线，一次性）

```
PDF/DOCX 模组
   ↓ 抽取文本（pypdf / python-docx，保留标题层级）
分块（按章节，带标题路径）
   ↓ 逐块 LLM 抽取（每块只抽"结构化片段"，不让它自由发挥）
候选 JSON（场景/线索/NPC/触发器/结局）
   ↓ 规则校验（必填字段、引用完整性：exits 指向的场景是否存在、线索 leads_to 是否有效）
人工校对（网页编辑器：左边原文、右边 JSON，逐条确认）
   ↓
落库（module 表，validated=1）
```

**关键：抽取阶段的 prompt 要"填空"而不是"创作"**——给 schema，让它只输出符合字段的 JSON；抽不到的字段留空，交给人补。**不要让它生成剧情。**

**入口与门槛（Q4）**：

- 优先**本地上传**（管理员把文件放进 `data/modules/`，或用 `/coc 导入模组` 发附件）；群文件引用作为 P2 可选（要 NapCat 拉群文件 + 类型校验）。
- 上传只是“进队列”：**未通过结构校验与人工校对的模组不能开局**（`module.validated=0` 时 `/coc 开始` 直接拒绝并说明原因）。
- 模组属版权内容，只在本机/本群使用，不落公网。

> 建议你在 P2 阶段提供 1-2 个自己写的小模组（或已授权的模组）做样板，先把 schema 打磨稳定，再碰长模组。

### 5.3 运行时：场景状态机

```
[scene A] --(找到线索X 且 玩家决定去B)--> [scene B]
     │                                        │
     └─(停留超过 N 轮 / 世界时钟到点)──────────┘
```

运行时职责：

1. 维护 `current_scene`；
2. 每次行动后检查 `exits` 条件与 `triggers`；
3. 维护"已发现线索"集合 → 决定给模型哪段 `player_text`；
4. **卡关检测**：主线线索长期未发现 → 提供"灵感/幸运/环境提示"的软出口；
5. 结局条件满足 → 进入 `ending`，生成本局结算。

### 5.4 剧透隔离的实现

| 数据                             | 进模型提示词？     |
| ------------------------------ | ----------- |
| `scene.player_text`            | ✅           |
| `scene.keeper_text`            | ❌（只在规则判定时用） |
| `clue.player_text`（已发现）        | ✅           |
| `clue.keeper_text` / 未发现线索     | ❌           |
| `npc.public_json` / 当前场景内的公开态度 | ✅           |
| `npc.secret_json`              | ❌           |
| `module.background`（真相）        | ❌           |

实现上就是：`build_prompt()` 只从"玩家可见视图"取值，`keeper_view()` 单独给规则引擎和 KP 私聊用。**这是数据层约束，不是提示词约束。**

## 6. 回合与行动控制

### 6.1 行动协议（KP 提问 → 玩家声明 → 结算 → 叙事）

一个回合的固定节奏：

```
KP： 【书房·夜】描述当前场景 + 明确"现在可以做什么"
      ↓（收集窗口，默认 90 秒）
玩家：自然语言声明（"我翻日记" / "我去门口守着" / "我先听一下门外"）
      ↓
KP： 按 DEX/声明顺序逐条结算
     「P1 侦查检定 d100=37/65 成功 → 你在日记夹层发现半张船票……」
      ↓
KP： 更新状态条 + 抛出下一场景/下一问
```

**为什么要"先收集再结算"**：群聊是异步的。如果来一条结算一条，先说话的人会把整轮节奏占满，后说话的人永远慢半拍。

### 6.2 多人排序与超时

| 情况   | 处理                                                |
| ---- | ------------------------------------------------- |
| 到齐   | 全部声明齐 → 统一结算                                      |
| 超时   | 未声明者视为"观望"，不阻塞（可配置"催促一次"）                         |
| 抢话   | 同一玩家多条声明 → 取最后一条有效的，或者合并（"我既翻日记又看窗外" → 拆成两个动作按顺序） |
| 挂机   | 连续 N 轮未声明 → KP 私聊提醒，仍无响应则转为"跟随队伍"                 |
| 动作冲突 | 两人同时开同一扇门 → 都执行，结果只叙述一次（避免重复消耗）                   |
| 中途加入 | 新玩家在**回合边界**入队；用"当前场景 + 已发生事实 + 公开角色卡"生成导入叙事（不给新人看 keeper 信息），记 `party_change` |
| 中途离开 | 角色转 NPC 托管或写离场理由；回合边界更新行动者集合，不凭空消失 |
| 单人行 | 1 人团时"声明-结算"退化为"声明即结算"，其余规则不变 |

### 6.3 秘密行动

- 玩家私聊 KP → KP 私聊返回结果，群内只播"某人似乎发现了什么"；
- 掷骰可见性三态（Q5）：`public` 群里公开骰点；`private` 骰点只私聊给行动者、群里只播叙事（即"秘密明骰"）；`kp_only` 连骰点都不给玩家（暗骰）。
- 私聊信息按"该玩家已发现 + 其角色能感知"过滤（Q10）：未绑定角色的私聊先要求 `/coc 角色` 绑定，不绑定就不回答；涉及他人角色数据一律拒绝；角色卡分 `public_view`（名字/职业/明显伤势）与 `private_view`（完整数值），只有本人与管理员能看完整。
- 这要求 `session` 支持"每条消息先判断来源是群还是私聊"，权限上只有本局 PC 能操作。

### 6.4 自然语言 → 结构化动作（解析策略）

**规则优先，模型兜底**：

1. 规则匹配：`/coc 行动 侦查 日记`、`/coc 去 书房`（显式命令，永远可靠）；
2. 关键词/正则：`翻|查看|检查 X` → investigate；`打|攻击|开枪 X` → attack；`问 X 关于 Y` → talk；
3. 模型兜底：把"当前场景可用动作列表 + 玩家原话"给模型，输出 `{action, target, approach}` 的 JSON；
4. 失败就**反问**："你是想（A）翻日记（B）检查书桌（C）别的？"——绝不自作主张。

> 关键：动作类型要有闭集（`investigate / move / talk / attack / dodge / use_item / skill_check / wait / custom`）。开放集合会让规则引擎无法处理。

### 6.5 对话通道：IC / OOC / 规则提问 / 密谈

群聊里玩家发出的消息混着四类意图，**必须先分流再处理**，否则模型会把"我想看一下卡"当成剧情行动：

| 类型      | 判定方式                        | 处理                     | 是否耗回合     |
| ------- | --------------------------- | ---------------------- | --------- |
| IC 台词   | 引号包裹（`"…"` 或「…」）            | 作为台词进叙事上下文，可能触发 NPC 回应 | 否（自由对话窗口） |
| IC 行动声明 | 无引号的陈述句                     | 进动作解析器（6.4）            | 是         |
| OOC 讨论  | `ooc:` / `//` / `（…）` 前缀或包裹 | 不进叙事，只回一句规则/界面解释       | 否         |
| 规则查询    | `/coc 规则 …`                 | 查规则条目（只读工具）            | 否         |
| 密谈      | 私聊 KP                       | 仅行动者与 KP 可见            | 是（秘密行动）   |

#### 6.5.1 三档信号：高置信 OOC / 灰色 / 高置信 IC

分流不靠模型，先靠信号强度（确定性、零成本、可测）：

| 档位 | 信号 | 例子 | 处理 |
|---|---|---|---|
| 高置信 OOC | 显式前缀、元词汇、第三人称指代角色 | `ooc: 我侦查多少`、`这NPC是不是有问题`、`SAN 还剩多少` | 直接进 OOC 通道 |
| 灰色地带 | 无引号、无元词汇、既像行动又像闲聊 | `我先看看门外`、`要不我们撤？` | 反问一次（6.5.3） |
| 高置信 IC | 引号台词、明确行动动词 | `我盯着老陈，问他昨晚去哪` | 进动作解析器 |

**元词汇表**（初始清单，可持续扩）：`NPC`、`PL`、`PC`、`KP`、`骰子`、`检定`、`技能值`、`模组`、`剧本`、`团`、`存档`、`角色卡`、`SAN`、`这游戏`、`规则上`。
出现元词汇、或第三人称指代本团角色（「这NPC」「我角色」），直接判高置信 OOC——「这NPC是不是有问题」属于这一档，不需要反问。

#### 6.5.2 OOC 通道：四不 + 两类受控影响

**四不是硬约束（代码层执行）**：

1. 不进叙事上下文（不写 `narrative`、不进 memory）；
2. 不耗回合（不推进 `turn_no`）；
3. 不触发检定（不产生 `roll`）；
4. 不改世界状态（不产生 `state_change` / `clue_found`）。

**只有两类允许的间接影响**：

- **排练**：OOC 里的意图不生效；玩家转成角色身份说一遍才进判定（`ooc: 我想去仓库` 不生效，`我走向仓库` 生效）。
- **调控信号**：OOC 里暴露的玩家状态（「这线索太难找了」「不太想看太血腥的」）可作为 KP 的卡点提示与内容强度信号——**只影响提示与尺度，不改判定与剧情事实**。

**回复渠道**：规则类在群里回一行、带 `（OOC）` 前缀；个人角色数据私聊回；纠正类私聊回；**永不公开点名「你刚才 OOC 了」**。

#### 6.5.3 灰色地带：反问一次，然后按类型默认收尾

灰色消息 → 反问一次（群里一行）：

`（OOC）你是要观察门外，还是只是说说？想动手就用角色身份说一遍。`

玩家没接（直接继续 IC 或沉默）时按**类型默认**收尾，而不是无限等待：

| 模糊消息类型 | 未接时的默认 | 理由 |
|---|---|---|
| 猜测 / 评论类（他是不是有问题） | 按 OOC：不答、不进叙事 | 按 IC 会剧透，代价远大于丢一句台词 |
| 行动 / 意图类（我看看门外） | 按 IC：正常执行 | 按 OOC 会让玩家行动白费，体验更差 |
| 纯提问（我能用图书馆吗） | 按 OOC：回答规则 | 规则问题不该进剧情 |

三条纪律：**只问一次**（pending 只保留最近一条，不叠问）、**不阻塞**（行动照常执行）、**不事后补答**（玩家跑去行动了，绝不补一句"其实他真有问题"，否则等于奖励忽略提问且剧透已发生）。玩家之后主动用 `ooc:` 再问，属合法元层，正常回答。

#### 6.5.4 默认判定必须留痕（可回看）

默认解析**不是偷偷替玩家做决定**，三个层面都要留痕：

| 层面 | 内容 | 谁能看 |
|---|---|---|
| 事件表 | `ooc_unresolved`：原文、默认值（OOC/IC）、触发原因（元词汇/超时/玩家继续行动）、时间、决策者=`default_policy` | 系统 / 复盘 / 管理员 |
| 运行日志 | 一行 INFO：`[coc] 默认解析 msg=<id> → OOC（原因=元词汇），未进叙事` | 运维 |
| 玩家侧 | 该玩家私聊一条极短回执：`（记录）刚才那句按 OOC 处理了；要算行动就再说一遍` | 当事人 |

**复盘单独列出**：本局发生几次默认判定、分别在哪一轮、原文是什么、采用哪个默认、是否影响剧情（正常应为"未进叙事"）。公开场合不点名、不广播——留痕是为了可追溯与可纠正，不是曝光玩家。

**自由对话窗口**：同一场景内 PC 之间聊天、和 NPC 闲聊，不推进回合。KP 只在被直接搭话或被 @ 时插话。这样避免"每句都调模型"，也让玩家敢说话。

### 6.6 NPC 对话引擎：知识白名单 + 语气

NPC 的台词**只能基于它自己知道的事**生成。每次生成给模型的材料：

| 给                   | 不给                  |
| ------------------- | ------------------- |
| 身份/态度/说话风格          | `keeper_text`（场景真相） |
| `knows` 白名单（它知道的情报） | 其他 NPC 的秘密          |
| 场景公共信息              | 未发现的线索              |
| 当前对话者是谁             | 玩家的 OOC 讨论          |

prompt 形态（示意）：

```
你是【老陈】，码头看守。说话短句、带方言、怕事。
你知道：昨晚看到局长搬箱子。
你不知道：箱子里是什么、灯塔的事、任何调查员的身份。
被问到不知道的事时，用搪塞/回避/害怕的方式回应，不要说「我不知道剧情」。
只输出一句台词（≤40 字），不要旁白，不要解释规则。
```

**套话机制**：关键信息放在 NPC 的 `won't_say_unless`（被吓到 / 被收买 / 话术检定成功 / 出示某物）里，**由规则判定是否解锁，不由模型决定**。模型只负责"解锁后怎么说"。

**台词优先级（Q6）**：每个 NPC 有 `line_policy`——`scripted_first`（默认：模组给了台词就原文输出、不改写，没有才让模型生成）/ `free`（全生成）/ `scripted_only`（只用脚本台词）。**关键情报（`key_info=true`）永远走 `won't_say_unless` 规则解锁**，不交给模型判断“该不该说”。

### 6.7 难度旋钮与 KP 风格

难度不是一句话，而是三层旋钮，每层都记进事件表：

| 层            | 旋钮                          | 影响                    |
| ------------ | --------------------------- | --------------------- |
| 全局（campaign） | `keeper_style`：宽松 / 标准 / 残酷 | 奖励骰倾向、失败后果强度、SAN 取值方式 |
| 场景（scene）    | `tension` 0–100             | 低张力给奖励骰、高张力给惩罚骰       |
| 单次判定（check）  | 难度等级、奖惩骰、是否允许孤注一掷           | 这一次检定的具体参数            |

档位具体化：

| 档位  | 默认奖励骰       | 失败后果                    | 主线线索       | SAN 损失    | 放水配额（Q14） |
| --- | ----------- | ----------------------- | ---------- | --------- | ---------- |
| 宽松  | +1（每场景首次尝试） | fail forward：失败也推进，但带代价 | 允许"换个方法再试" | 取给定区间的最小值 | 每场景 3 次    |
| 标准  | 0           | 失败停步，可孤注一掷              | 需要检定       | 正常掷       | 每场景 2 次    |
| 残酷  | 高压场景 −1     | 失败即恶化（受伤/暴露/时间流逝）       | 可能错过，靠软提示补 | 取最大值      | 每场景 0–1 次  |

> 残酷档不是"完全不给余地"：**fail-forward 仍然保留**（它是推进剧情的手段，不是帮玩家赢），只取消奖励骰与后果软化；否则主线卡点会 100% 卡死。

`tension` 曲线：进入新场景 +20、发现关键线索 −10、进入战斗 +30、安全屋休息 −40；每 10 点张力折算 ±1 颗奖励/惩罚骰，上下限 ±2。

### 6.8 放水：四种手段、配额与透明性

**总原则：不改骰子，只改后果与信息。** 骰点保持真实（可验证、可复盘），KP 的调控体现在"这一掷之后发生什么"。

| 手段           | 具体做法                           | 适用时机       |
| ------------ | ------------------------------ | ---------- |
| 给奖励骰         | 下一次同类检定 +1                     | 玩家准备充分但运气差 |
| Fail forward | 失败也推进，但附带代价（受伤/丢物品/时间流逝/敌人警觉）  | 主线卡点       |
| 给信息          | 环境细节、NPC 暗示、免费"灵感"提示（只说方向不给答案） | 线索卡住 ≥2 轮  |
| 软化后果         | 伤害减半、SAN 取小值、敌人撤退、被俘而非死亡       | 会导致团灭/秒杀时  |

配额与红线：

- 配额绑定难度档位（Q14）：宽松 3 次/场景、标准 2 次、残酷 0–1 次；另有**每局 6 次**全局上限，防止多开场景刷额度。每次写一条 `keeper_mercy` 事件（含原因）。
- **不适用**：终局判定、玩家主动作死（例如明知危险还去踢邪神）、PVP。
- **玩家无感**：叙事上要自然，不能出现"我帮你降难度了"。
- **复盘透明**：战报里标注"此处使用了 1 次 fail-forward"。

反例（禁止）：改骰点、把大失败说成成功、直接取消死亡（应改为重伤/被俘/失去关键物品）。

### 6.8.1 世界推进（world_tick）：卡关兜底的第二档

卡关兜底分三档，**世界推进不是放水**：

| 档 | 手段 | 是否放水 | 上限 |
|---|---|---|---|
| 1 | 软提示（环境细节 / NPC 暗示 / 灵感） | 是 | 每场景 2 次（占放水配额） |
| 2 | 世界推进（时间流逝、反派行动、局势恶化） | 否 | 每场景 1 次 / 每局 3 次 |
| 3 | 结局分支（线索永久丢失，进入失败线） | 否 | 不设限（自然发生） |

世界推进的三条边界（Q7）：

1. **不直接给线索**——只改变局势与压力（"你们耽搁的这段时间，港口又少了一艘船"）；给了线索就变成变相放水；
2. **不占放水配额**，但必须记 `world_tick` 事件，并在群里给出可见的"时间流逝"提示；
3. **推演后留一个"最后窗口"**——一次阻止/挽回的机会，否则玩家会觉得 KP 自己把团跑完了。

### 6.9 捣乱玩家：先把 IC 与 OOC 分开

| 类型           | 例子                  | 处理                          |
| ------------ | ------------------- | --------------------------- |
| IC 捣乱（角色行为）  | 踢门、挑衅邪教徒、坑队友、作死     | **不罚**，世界给自然反应，后果自负——这是跑团乐趣 |
| OOC 捣乱（破坏体验） | 刷屏、剧透、抢别人行动、伪造骰子、辱骂 | 分级处理，见下                     |

分级处理：

| 级别    | 行为          | 处理                                        |
| ----- | ----------- | ----------------------------------------- |
| L1 提示 | 连续多条、抢话     | KP 合并处理（只取最新一条有效声明），私聊提醒"一句一句来"           |
| L2 机制 | 替别人声明行动     | 忽略他人声明，只执行本人的                             |
| L3 剧透 | 说出未发现的线索/真相 | 该信息在剧情中"不存在"（NPC 改口/线索转移），并记 `disrupt` 事件 |
| L4 伪造 | 声称自己掷了某个点数  | 以系统骰为准，不解释、不争论                            |
| L5 人际 | 辱骂、骚扰、恶意破坏  | **交给真人管理员**（禁言/移出），AI 不做审判                |

三条红线：

1. **AI 不执行社交处罚**——不禁言、不踢人、不公开点名羞辱；
2. **AI 不用游戏机制惩罚现实冲突**——不扣幸运、不针对角色；
3. **所有 `disrupt` 事件进复盘**，供管理员事后判断，而不是当场升级。

### 6.10 这些调控如何进入复盘

事件类型扩充：`ooc` / `ooc_unresolved` / `ooc_correction` / `npc_talk` / `tension_change` / `keeper_mercy` / `world_tick` / `party_change` / `disrupt` / `character_import`。

战报中新增指标：放水次数与位置、难度调整记录、玩家违规类型分布、每个场景的卡关时长。

用途：判断这个团是不是"太松/太严"、哪些线索总是卡住、是否需要人工介入某个玩家。**调控本身也要被复盘**，否则放水会变成习惯性作弊。

## 7. 与 suggarchat 的对接

### 7.1 接线方式

```
coc_keeper/matcher（block=True）  ← 跑团群里的 /coc 命令与"当前回合的玩家发言"
        │
        ├─ 自己拼 prompt（事实包）→ 调 LLM（或经 suggarchat 的钩子）
        └─ 发送叙事（自己发，格式可控）

sugggarchat 的钩子（可选，二选一）：
  on_before_chat：注入事实包（让 suggarchat 生成）
  on_chat：收尾（截断/去元叙述/分条）
```

**建议**：P1 先用"自建 matcher + 直接调 LLM"，因为格式、长度、温度、重试都在自己手里；等叙事风格稳定后，再把"NPC 逐句对话"这种高频短回合交给 suggarchat 的钩子处理。这样不会一开始就陷入"改 suggarchat 行为"的泥潭。

### 7.2 上下文分层（每回合只拼必要部分）

| 层       | 内容                            | 大约 token |
| ------- | ----------------------------- | -------- |
| L1 系统   | KP 身份、输出格式（只输出正文、2-4 句、不要元叙述） | 150      |
| L2 规则摘要 | 只放"本回合可能用到的规则"（如本次检定类型）       | 100      |
| L3 场景   | 当前场景 `player_text` + 已发现线索摘要  | 300-600  |
| L4 角色   | 在场 PC/NPC 的公开信息（一句话人设 + 当前状态） | 200-400  |
| L5 记忆   | 前情摘要（每场景结束生成一次，不复用聊天记忆）       | 200-400  |
| L6 本回合  | 玩家声明 + 解析结果 + 骰点结果 + 状态变更     | 200-300  |
| 输出      | 叙事正文                          | 300-500  |

**不要**把整段对话历史喂进去。前情用"每场景一次摘要"来压缩，摘要由模型生成、程序存库、下次直接读。

### 7.3 输出约束（写进系统提示词）

- 只输出叙事正文，不输出"作为 KP""判定结果如下""我建议你……"；
- 2-4 句，最多 120 字（QQ 群阅读体验 + token 成本）；
- 不复述骰点（骰点由程序单独发一条状态行）；
- 不透露未发现的线索、不在场的 NPC 行为、`keeper_text`；
- 角色台词前加名字（`【老陈】"……"`），旁白不加。

### 7.4 输出形态

| 消息   | 谁发      | 形态                                       |
| ---- | ------- | ---------------------------------------- |
| 场景描写 | 叙事器     | 文本（可配 1 张手图/场景图）                         |
| 检定结果 | 程序      | 固定格式一行：`🎲 侦查 37/65 成功`                  |
| 状态条  | 程序      | `HP 11/12 ｜ SAN 48/55 ｜ MP 9/12 ｜ 幸运 40` |
| 结局   | 程序 + 叙事 | 结算表 + 叙事收尾                               |
| 战报   | 复盘器     | 群内摘要 + 网页/文件                             |

### 7.5 Token 与成本估算（DeepSeek）

| 项   | 每回合        | 一局（60 回合）   |
| --- | ---------- | ----------- |
| 输入  | ~1.2k-1.8k | ~90k        |
| 输出  | ~0.4k      | ~24k        |
| 合计  | ~2k        | ~114k token |

按 DeepSeek 现价（输入 ~1 元/百万、输出 ~2 元/百万量级）估算，**一局成本在几毛钱**。真正的成本风险不是单价，而是**重试/幻觉导致的无效调用**——所以解析失败要反问，不要反复重试生成。

### 7.6 要不要给模型 agent / 工具调用能力？

**结论：分场合。实时跑团主循环只给「只读工具 + 结构化动作」，不给「改状态」的工具；完整 agent loop（模型自主多轮调工具）只用在离线环节（模组导入、战报生成）。**

#### 三种形态对比

| 形态             | 模型能做什么                   | 适合                  | 主要风险                      |
| -------------- | ------------------------ | ------------------- | ------------------------- |
| A 全 agent      | 自主决定查什么、改什么、推进到哪，可多轮工具调用 | 离线导入、战报生成（有人校对、可回滚） | 状态不可信、不可复现、成本与延迟高、会绕过回合闸门 |
| B 无工具（纯提示词）    | 只把事实包写成叙事                | P1 主循环              | 模型心算规则会错（用「规则摘要」缓解，但治不了根） |
| C 结构化动作 + 只读工具 | 输出 JSON 动作；叙事前可调只读工具自查   | **推荐：P2/P3 主循环**    | 需要一次 JSON 解析与校验           |

#### 主循环为什么不要 A

1. **状态权威性**：跑团最怕「事实错了」。模型改 HP/SAN/线索，一旦算错或幻觉，整局崩，而且玩家会立刻发现。
2. **不可复现**：工具调用发生在 suggarchat 的 agent loop 内部，调用轨迹默认不进我们的库；复盘、争议仲裁、bug 复现都缺数据。
3. **回合闸门**：agent 会自己决定「再推进一个场景 / 再问一句」，破坏「声明-结算」节奏；群聊里表现为连发多条、抢走玩家行动权。
4. **多人会串台**：suggarchat 的记忆与工具上下文是 per 聊天对象，不区分「现在是谁在行动」；三人同时声明时容易把 A 的检定结果写给 B。
5. **延迟与成本**：每次工具调用多一轮 LLM（+2-5 秒、+1-2k token）。群聊跑团对延迟很敏感，一回合拖到 30 秒玩家就散了。
6. **已知坑**：本项目文档 3.12.4 记录过——`enable_tools` 开着但没有可用工具时，模型会「假装调用工具」并复读；`agent_mode_enable` 默认关闭也是同一原因。开 agent 前要先解决这个行为问题。

#### 值得给的只读工具（白名单）

| 工具                                 | 返回                         | 为什么值得给                   |
| ---------------------------------- | -------------------------- | ------------------------ |
| `get_character(name/qq)`           | 角色卡**公开视图**                | 避免模型记错技能值、把 A 的技能算到 B 头上 |
| `get_party_status()`               | HP/SAN/MP/幸运状态条            | 叙事里引用状态时不必心算             |
| `get_scene_view()`                 | 当前场景 `player_text` + 已发现线索 | 保证描写不跑出场景                |
| `get_discovered_clues()`           | 玩家已知线索摘要                   | 避免「忘了玩家已经知道」或重复发现        |
| `query_rule(keyword)`              | 规则条目（RAG 检索）               | 规则问答/判定解释，别让模型背规则        |
| `preview_check(skill, difficulty)` | 成功率数字（**不掷骰**）             | 玩家问「我这枪几成」时给准确答案         |

共同点：**全都不改变游戏状态**（最多写一条审计日志）。它们的价值是消灭「记错 / 心算错 / 说漏」。

#### 绝对不能给模型直接调用的

`apply_damage`、`set_san`、`add_clue`、`move_scene`、`advance_turn`、`end_session`、`award_item`。

这些只能由程序在「解析玩家动作 → 合法性校验 → 掷骰 → 落事件」之后执行。模型最多「提议」，不能「落子」。

#### 更推荐的替代：结构化动作协议（单轮，无循环）

模型只输出一个 JSON，程序负责其余一切：

```json
{"action": "investigate", "target": "日记", "approach": "翻找夹层", "say": "我蹲下来翻那本日记"}
```

流程：`校验 → 掷骰 → 执行 → 写事件 → 回灌事实包 → 模型写叙事`。
好处：零依赖、可单测、可回放、每回合固定一次调用（成本可预测）。这本质上就是「去掉循环的 function calling」，把不确定性关在笼子里。

#### 那什么时候值得上完整 agent

| 环节           | 为什么合适                                        | 形态         |
| ------------ | -------------------------------------------- | ---------- |
| 模组导入与校对      | 离线、有人审、可回滚：抽一段 → 写 scene/clue → 自检引用 → 再抽下一段 | A（全 agent） |
| 复盘战报生成       | 只读事件表，边查边写，天然只读                              | A 或 C      |
| 规则问答 / 车卡助手  | 需要检索规则与模板                                    | C（只读工具）    |
| NPC 自由对话（P3） | 需要「这个 NPC 知道什么」的检索；仍旧只读                      | C（只读工具）    |

#### 如果真要用 suggarchat 的工具机制（工程细节）

suggarchat 3.7.0 已经提供现成的工具注册接口，不用改源码：

```python
from nonebot_plugin_suggarchat.utils.llm_tools.manager import on_tools
from nonebot_plugin_suggarchat.utils.llm_tools.models import (
    FunctionDefinitionSchema, FunctionParametersSchema, ToolContext,
)

@on_tools(
    FunctionDefinitionSchema(
        name="coc_get_party_status",
        description="查询当前跑团小队的公开状态（HP/SAN/MP/幸运）。只读。",
        parameters=FunctionParametersSchema(type="object", properties={}, required=[]),
    ),
    show_call=False,                                        # 别在群里播「正在调用工具」，破坏沉浸感
    enable_if=lambda: coc_runtime.has_running_session(),     # 只在跑团进行时可用
)
async def coc_get_party_status(ctx: ToolContext) -> str:
    # ctx 里有 event / bot / matcher，能拿到群号与 QQ，可以在工具内部做权限校验
    return json.dumps(coc_runtime.party_status_view(ctx.event), ensure_ascii=False)
```

要点：

- `ToolContext(data, event, matcher, bot)` 能拿到事件上下文，**工具内部必须自己校验「这个群的这个玩家有没有权限」**；
- `enable_if` 做「仅在跑团会话期间启用」，避免污染日常聊天；
- `show_call=False`，否则群里会冒出「正在调用工具」的系统提示；
- **把工具调用写进事件表**（在工具函数里 append 一条 `tool_call` 事件），否则复盘断链；
- `agent_mode_enable=false`、`agent_tool_call_limit=1`，把它当「单轮查询」用，不要当循环；
- 打开 `enable_tools` 前先确认不会复读（历史上踩过）。

#### 一句话

> 让模型「查」可以，让它「改」不行；让模型「演」可以，让它「定」不行。

## 8. Replay（复盘）

### 8.1 从事件表生成

```
event 表 → 按 seq 重放 → 归类为：
  ├─ 场景流：进过哪些场景、停留几回合
  ├─ 行动流：谁做了什么、成功失败
  ├─ 骰点表：技能 / 目标 / 骰值 / 结果（明骰 + 暗骰分列）
  ├─ 线索表：发现/遗漏的主线线索（含"本应可发现却错过"）
  ├─ SAN 曲线：每次损失与当前值
  ├─ 战斗记录：轮次、伤害、重伤
  └─ 结局评价：达成哪个结局、关键决策点
```

### 8.2 输出形态（按需分三档）

| 档    | 内容                    | 场景              |
| ---- | --------------------- | --------------- |
| 群内摘要 | 300 字 + 关键骰点 + 结局     | 一局结束时自动发        |
| 网页战报 | 完整时间线，可折叠，带 SAN 曲线图   | 配置台「跑团」页 → 战报列表 |
| 导出文件 | Markdown / HTML / PDF | 存档、分享           |

**两个版本（Q8）**：`玩家版` 只含玩家可见信息（明骰、已发现线索、无 keeper 内容），导出 md/PDF 后**上传到群文件**；`KP 版` 额外含暗骰、放水记录、默认判定记录，只给管理员（配置台/本地）。上传失败重试 3 次，仍失败则回落为群内摘要。

### 8.3 复盘的科学价值（顺带做）

- **平衡性观察**：哪类检定失败率异常（可能是难度设置有问题）；
- **线索遗漏率**：哪些线索从来没人发现（设计问题或提示不足）；
- **节奏**：平均每场景几回合（判断模组长度是否合适）；
- **KP 风格一致性**：输出长度分布、检定频率。

这些指标能让"AI 当 KP"从"能跑"走向"跑得好"。

### 9.2 配置台新增「跑团」页（复用 ai_config_console 模式）

| 视图   | 内容                                                |
| ---- | ------------------------------------------------- |
| 角色卡  | 列表 + 编辑器（属性/技能/物品/背景），NPC 与 PC 分栏，NPC 的"秘密面"单独折叠区 |
