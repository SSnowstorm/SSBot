# SuggarChat 日常管理与省 Token 设计案

> 版本：v1.1（2026-08-15）  
> 适用范围：SSBot 项目内 nonebot-plugin-suggarchat 3.7.0（DeepSeek chat）  
> 目的：日常使用便于管理与维护 + 尽可能省 Token；本设计案同时作为后续自定义改造的蓝图  
> 依据：全部结论均来自插件源码核实（`site-packages/nonebot_plugin_suggarchat/`）与当前 `config.toml` 实际配置

---

## 0. 结论先行（TL;DR）

- **最大省 Token 点只有一个：内容安全检查（enable_report）**。它让每条消息产生**两次** LLM 调用（一次检查 + 一次对话），且检查时默认携带完整系统提示 + 全部上下文。收紧或关闭它，输入 Token 可省约 40%~50%。
- **第二大项：记忆长度（memory_lenth_limit=50）**。50 条历史消息每次都完整发给模型，压到 20~30 条立竿见影，代价是长程记忆变弱（有摘要机制兜底）。
- **管理与维护的核心配套是打开用量限额（usage_limit）**——当前全部关闭，等于没有任何"烧钱保险丝"。
- 其余优化（戳一戳回复、合并转发解析、人格文件精简、日志级别）都是小项，但零成本可做。
- 所有 A 级优化都是**改 config.toml 即可**，不改代码、不重启（UniConfig 热重载）。
- **v1.1 扩充**：第 3 章从"运维技术要点"升级为"管理体系"——补齐角色与责任、例行节奏、变更流程、成本/安全治理与度量指标，管理落地为可执行制度。

## 1. 现状盘点：一条消息的 Token 流向

### 1.1 请求链路（源码核实）

```
群/私聊消息
  │
  ├─[1] checkhook 内容安全检查 (builtin_hook.py:67)
  │      enable_report=true → 用【主模型】调一次 LLM（REPORT 工具判断是否违规）
  │      默认携带：完整系统提示 + 全部记忆上下文 + 用户消息（report_exclude_* 均未开）
  │      判定违规 → 熔断（清记忆 + 返回 block_msg），不进入主对话
  │
  └─[2] 主对话 get_chat (chatmanager.py:711)
         输入 = 系统提示(train) + 记忆上下文(memory.messages)
         系统提示 = SCHEMA模板 + <SYSTEM_INSTRUCTIONS>人格文件 + <SUMMARY>摘要 + <EXTRA>自定义prompt
         输出 = max_tokens=500
         （会话超长时 MemoryLimiter 还会额外调一次 LLM 生成摘要）
```

### 1.2 Token 消耗构成（每次消息）

| 项                | 位置                          | 当前值                | 是否每次固定开销            |
| ---------------- | --------------------------- | ------------------ | ------------------- |
| SCHEMA 模板        | chatmanager.py:607-613      | ~300 字             | 是                   |
| 人格文件内容           | group/private_prompts/*.txt | 空文件（0 Token）       | 是，随文件变长而增加          |
| 上下文摘要 SUMMARY    | <SUMMARY> 标签                | 启用，摘要内容            | 是                   |
| 自定义 prompt EXTRA | /prompt 设置                  | 未设置                | 是（仅当设置过）            |
| 历史消息             | memory.messages             | 最多 50 条            | 是（随会话变长而增加）         |
| **内容安全检查输入**     | checkhook                   | **= 系统提示 + 全部上下文** | **是（等于把上面的输入再花一遍）** |
| 输出               | max_tokens                  | 500                | 否                   |

### 1.3 量化示例（估算）

假设：系统提示 500 Token + 50 条历史消息 3000 Token：

| 场景         | 每次输入 Token | 说明                 |
| ---------- | ---------- | ------------------ |
| 当前（检查全量）   | ≈ 7000     | 主对话 3500 + 检查 3500 |
| 检查只查最后一条消息 | ≈ 3550     | 主对话 3500 + 检查 ~50  |
| 关闭检查       | ≈ 3500     | 仅主对话               |

**结论：内容检查是唯一能把输入成本翻倍的项目，优先级最高。**

## 2. 省 Token 方案（分三级）

### 2.1 A 级：配置级，零代码（推荐先做）

| #  | 配置项                                                                      | 现状          | 建议值                     | 预期收益                             | 风险/代价                                                 |
| -- | ------------------------------------------------------------------------ | ----------- | ----------------------- | -------------------------------- | ----------------------------------------------------- |
| A1 | `llm_config.tools.enable_report`                                         | true        | **false**（完全关闭）或按 A2 折中 | 输入 Token 省 ~50%                  | 失去内容审查；若有"违规熔断"需求需另想办法                                |
| A2 | 折中方案：`report_exclude_system_prompt=true` + `report_exclude_context=true` | false/false | true/true               | 检查输入从"全部上下文"降到"仅用户最后一条消息"，省 ~45% | 仍保留一次检查调用（省的是检查的输入，不是调用次数）；审查只针对单条消息，上下文型违规（诱导、套话）查不到 |
| A3 | `llm_config.memory_lenth_limit`                                          | 50          | **20~30**               | 历史消息 Token 减半以上                  | 长程记忆变弱；靠摘要机制部分兜底                                      |
| A4 | `function.poke_reply`                                                    | true        | **false**（如不想要戳一戳回复）    | 戳一戳不再触发 LLM 调用                   | 功能丢失                                                  |
| A5 | `function.synthesize_forward_message`                                    | true        | **false**（如群里少用合并转发）    | 合并转发大段内容不再展开进上下文                 | 群里发合并转发时回复质量下降                                        |
| A6 | `llm_config.max_tokens`                                                  | 500         | 保持或 300                 | 输出 Token 上限收紧                    | 长回答被截断                                                |
| A7 | 人格文件                                                                     | 空 default   | 建精简场景人格（见 3.2）          | 内容可控；顺带解决群/私混淆                   | 无（写得太长反而费 Token，需克制）                                  |

### 2.2 B 级：日常使用习惯（管理行为，零配置）

| #  | 动作                                                 | 收益               |
| -- | -------------------------------------------------- | ---------------- |
| B1 | 长会话定期 `/del_memory` 清上下文（或开启 session_control 自动清理） | 历史消息不再膨胀，直接降每次输入 |
| B2 | 用 `/insights` 每日看 Token 用量，形成基线                    | 监控趋势，异常及时发现      |
| B3 | 群聊保持短句交流，不把大段文档贴给机器人                               | 上下文增量最小          |
| B4 | 不轻易用 `/prompt` 设置自定义 prompt（EXTRA 会进每次请求的系统提示）     | 避免隐藏的固定开销        |

### 2.3 C 级：结构性改造（需写代码，见第 4 章）

- 内容审查改走**便宜模型**（不让 deepseek-chat 干审查的活）
- 记忆/上下文策略按群定制（MemoryLimiter 子类化）
- 系统 SCHEMA 精简（覆盖 chatmanager 的 train 构造）

## 3. 管理体系

### 3.0 角色与责任矩阵

| 角色    | 人员            | 权限范围                     | 责任                    |
| ----- | ------------- | ------------------------ | --------------------- |
| 系统管理员 | 你（SUPERUSERS） | 全部命令 + 不受 usage_limit 限制 | 配置变更、人格文件上线、成本监控、故障处理 |
| 群管理员  | 各群群主/群管       | `/enable` `/disable`     | 该群开/关与刷屏熔断            |
| 普通用户  | 群员/私聊用户       | 聊天、`/insights`（查自己）      | 无管理责任                 |

**关键原则**：`[admin] admins` 保持空，权限单一来源 SUPERUSERS；群管只授"开关权"不授"改人格权"，避免人格被乱改导致 Token 失控。

### 3.1 例行管理节奏

| 频率       | 动作                | 工具/命令                    | 目的                |
| -------- | ----------------- | ------------------------ | ----------------- |
| 每日（1 分钟） | 看用量与成本            | `/insights`              | 发现异常（某群暴涨）        |
| 每日       | 扫一眼日志有无报错         | bot 控制台（INFO 级）          | 早期发现插件异常          |
| 每周       | 人格文件 review       | 查看 group/private_prompts | 确认无失控内容、文件无偷偷变长   |
| 每周       | 校准 usage_limit 阈值 | config.toml              | 按实际用量微调           |
| 每月       | 成本小结 + 备份恢复演练     | 备份恢复                     | 确认 db.sqlite3 可恢复 |
| 每次改动     | 变更记录登记            | 文档"变更记录"表                | 留痕可回溯             |

> 节奏可按实际调整：若日常无精力每日看，可降为"每周基线 + 每日只看告警"（待确认项 9）。

### 3.2 变更管理流程

**流程闭环**：变更申请 → 备份现状 → 执行变更 → 验证 → 登记变更记录

| 步骤   | 动作                              | 说明                  |
| ---- | ------------------------------- | ------------------- |
| 1 申请 | 确认变更内容与理由                       | 你确认后执行              |
| 2 备份 | config.toml + 人格目录 + db.sqlite3 | 入库 git 或复制到项目 docs/ |
| 3 执行 | 改 config.toml / 增删人格文件          | 热重载即生效，无需重启         |
| 4 验证 | `/test_preset` 或实测对话            | 确认行为符合预期            |
| 5 登记 | 附录"变更记录"表追加一行                   | 含日期、内容、修改人          |

**人格文件治理**（配合 3.7）：

- **命名规范**：`场景_用途.txt`（如 `私聊_默认.txt`、`群聊_默认.txt`），避免"猫娘"这类无语义命名散落
- **上线前置检查**：单文件 ≤200 字、无系统指令越狱语句、有场景边界说明（防群/私混淆）
- **版本控制**：入库 git，改版走变更记录

### 3.3 成本治理（含用量限额）

**预算闭环四层**：

| 层  | 设计                                      | 说明           |
| -- | --------------------------------------- | ------------ |
| 预算 | 设**月度 Token 预算**（先观察一周 /insights 再定具体值） | 超出当月封顶或降级    |
| 告警 | 用量超日基线 **2 倍** → 检查原因                   | /insights 对比 |
| 熔断 | usage_limit 兜底（下表）                      | 管理员豁免        |
| 报告 | 每月底成本小结                                 | 登记在变更记录表     |

`[usage_limit]` 当前全部默认（关闭），建议开启：

```toml
[usage_limit]
enable_usage_limit = true
group_daily_limit = 100        # 单群每日 100 次
user_daily_limit = 100         # 单用户每日 100 次
group_daily_token_limit = 200000   # 单群每日 20 万 Token（约 ¥0.2~0.4）
user_daily_token_limit = 100000    # 单用户每日 10 万 Token
total_daily_limit = 1500
total_daily_token_limit = 1000000
```

- 管理员（SUPERUSERS）**不受限额约束**（usage_enough 中豁免）
- 触发限额后用户会收到提示；用 `/insights` 查今日用量
- 阈值可按实际日用量（先观察一周 `/insights` 数据）再校准

### 3.4 内容安全与数据治理

| 事项   | 设计                                                                      |
| ---- | ----------------------------------------------------------------------- |
| 熔断日志 | 内容检查开启时，把触发 block_msg 的消息记日志（时间/群/用户/内容），供审计与误杀排查——上次"展示人格被拒"能快速定位即靠此思路 |
| 记忆数据 | 不重要的群/人定期 `/del_memory`；db.sqlite3 含聊天记忆，备份注意存放位置（脱敏/项目外）               |
| 误杀申诉 | 用户遇"无法处理"兜底回复 → 管理员查熔断日志判断误杀 → 决定是否调整                                   |

> 依赖项：熔断日志设计仅在内容检查（enable_report）开启时有意义；若最终选择 A1 完全关闭检查，此节退化为"统计 block_msg 出现次数"。

### 3.5 管理度量指标

| 指标         | 定义            | 健康阈值（建议）           |
| ---------- | ------------- | ------------------ |
| 日均 Token/群 | /insights     | 稳定，无突增             |
| 熔断次数/周     | 日志统计          | <3 次（多了说明误杀或有人在试探） |
| 人格文件大小     | 文件字数          | 全部 ≤200 字          |
| 配置漂移       | 与 git 备份 diff | 应为 0（改动必须走变更记录）    |

### 3.6 配置管理

| 事项    | 现状                                                               | 建议                                                 |
| ----- | ---------------------------------------------------------------- | -------------------------------------------------- |
| 配置入口  | `AppData\Roaming\nonebot2\nonebot_plugin_suggarchat\config.toml` | 唯一修改入口；敏感值用 `${ENV}` 占位（已用 DEEPSEEK_API_KEY）       |
| 配置热重载 | UniConfig 目录监控                                                   | 改完即生效，无需重启 bot；改后可用 `/test_preset` 验证              |
| 配置备份  | 无                                                                | 备份 config.toml + 人格目录 + models 目录到项目 `docs/` 或 git |
| 变更记录  | 无                                                                | 建议在本文件"变更记录"小节登记每次配置改动（见附录）                        |

### 3.7 人格文件管理（顺带解决群/私混淆）

目录结构（建议补齐两份场景人格，替换空的 default.txt）：

```
AppData\Roaming\nonebot2\nonebot_plugin_suggarchat\
├─ group_prompts\
│   ├─ default.txt      ← 空文件（建议内容化或删除）
│   └─ 群聊助手.txt      ← 新建：写明"你正在QQ群中"
└─ private_prompts\
    ├─ default.txt      ← 空文件（建议内容化或删除）
    └─ 私聊助手.txt      ← 新建：写明"你正在与用户一对一私聊，不是群聊；不要用群友/群员/入群等群聊用语；直接回答，不要输出'XX: 内容'格式"
```

- 切换命令：`/choose_prompt group 群聊助手`、`/choose_prompt private 私聊助手`
- **省 Token 约束**：人格内容每次请求都进系统提示，**单文件建议控制在 200 字以内**，只写场景边界和风格要点
- 备份：人格文件建议入库 git（AppData 目录在系统盘，重装会丢）

### 3.11 应急预案

| 场景      | 动作                                       |

## 4. 未来自定义改造蓝图

### 4.1 钩子点（matcher_function=true 已开启，可零侵入挂接）

| 钩子                                | 触发时机    | 可做的事                                                   |
| --------------------------------- | ------- | ------------------------------------------------------ |
| `on_before_chat`（BeforeChatEvent） | 消息发给模型前 | 按群/私注入场景标注（解决本次群/私混淆）、精简/改写发给模型的消息（省 Token 的 C 级改造都在这） |
| `on_chat`（ChatEvent）              | 模型回复后   | 改写回复、过滤格式泄露（如"SS: 时间 内容"复读）                            |
| `on_tools`                        | 工具调用    | 自定义工具                                                  |

### 4.2 建议改造点（按优先级）

| #  | 改造           | 方式                                              | 收益                 | 风险                             |
| -- | ------------ | ----------------------------------------------- | ------------------ | ------------------------------ |
| C1 | 群/私场景自动标注    | 注册 BEFORE_CHAT 钩子，按事件类型在系统提示追加"当前场景：私聊/群聊"      | 根治群/私混淆，替代人格文件方案   | 低（钩子方式，升级不覆盖）                  |
| C2 | 内容审查走便宜模型    | 自定义 checkhook 替代内置（内置用主预设 `_determine_presets`） | 检查调用成本降到 ~0        | 中（需维护自定义钩子，关闭内置 enable_report） |
| C3 | 系统 SCHEMA 精简 | 覆盖 train 构造（BEFORE_CHAT 钩子替换 system 消息）         | 每次请求固定省 300+ Token | 中（SCHEMA 承担功能约束，精简需谨慎）         |
| C4 | 记忆策略按群定制     | MemoryLimiter 子类化                               | 高活跃群短记忆、私聊长记忆      | 中                              |
| C5 | 防格式泄露        | CHAT 钩子过滤回复中"角色: 时间 内容"样式的模型自述                  | 提升体验               | 低                              |

### 4.3 改造纪律（重要）

- **优先用钩子/子类化，不要直接改 site-packages 源码**——升级插件会覆盖，且难维护
- 如必须改源码：在项目内记录 patch 清单（文件、行、改动、原因），升级后重新应用
- 所有改造保持"配置可回退"：新增配置项 + 默认关闭，不破坏现网

## 6. 待确认问题清单

1. **内容审查**：完全关闭（A1）还是只查最后一条消息（A2）？——这是最大的省 Token 项，但涉及安全权衡
2. **记忆长度**：压到 20 还是 30 条？
3. **用量限额**：是否开启？阈值用默认（100 次/群/日）还是自定义？
